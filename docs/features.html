YAML Agent Builder — Feature Reference

24 Mastra v1 features mapped to declarative YAML syntax

24 features
#1 Project Config declarative ✅ done ▼

What it's for

The root configuration file that wires the entire project together. Declares which agents to register, global logger settings, and shared infrastructure. Every YAML Agent Builder project starts here.

Syntax

config.yaml
name: my-assistant
agents:
  - support-agent
  - research-agent
logger:
  level: info
#2 Agents declarative ✅ done ▼

What it's for

Defines an AI agent with its identity, model, and toolset. Each agent lives in its own file under agent/. The codegen emits a new Agent({...}) call populated from these fields.

Syntax

agent/support-agent.yaml
name: Support Agent
description: Handles customer support queries
model: gpt-4o
tools:
  - echo-tool
  - search-tool
#3 Models declarative ✅ done ▼

What it's for

Defines a reusable LLM configuration (provider, model name, temperature, token limits) that can be referenced by multiple agents. Avoids repeating provider config across every agent YAML.

Syntax

model/gpt-4o.yaml
provider: openai
model: gpt-4o
temperature: 0.7
max_tokens: 2048

Agent reference

agent/support-agent.yaml
model: gpt-4o  # references model/gpt-4o.yaml
#4 Tools author-as-code ✅ done ▼

What it's for

Extends agent capabilities with callable functions. You write the tool logic in TypeScript using Mastra's createTool, then reference it by id in any agent YAML. The codegen imports and wires it automatically.

Syntax

tools/echo-tool.ts
import { createTool } from "@mastra/core/tools";
import { z } from "zod";

export const echoTool = createTool({
  id: "echo-tool",
  description: "Echoes back the input",
  inputSchema: z.object({
    message: z.string(),
  }),
  execute: async ({ context }) =>
    ({ output: context.message }),
});
agent/support-agent.yaml
tools:
  - echo-tool  # → tools/echo-tool.ts
#5 Prompts author-as-code ✅ done ▼

What it's for

Stores agent system prompts as standalone Markdown files so they can be version-controlled, edited by non-developers, and reused across agents. Referenced via the agent's instructions field.

Syntax

prompt/support-prompt.md
You are a helpful customer support agent.
Always be polite and concise.
Escalate complex issues to a human agent.
Never share customer PII in responses.
agent/support-agent.yaml
instructions: support-prompt
# reads from prompt/support-prompt.md
#6 Logger declarative ✅ done ▼

What it's for

Configures the Mastra logger verbosity for the entire project. Controls how much output appears during agent runs — useful for debugging tool calls, model responses, and step traces.

Syntax

config.yaml
logger:
  level: info  # debug | info | warn | error
#7 Storage declarative ✅ done ▼

What it's for

Configures the persistent storage backend used for conversation history, agent state, and memory. Mastra supports libSQL (local or Turso), PostgreSQL, and others. A required foundation for memory features.

Syntax

config.yaml
storage:
  type: libsql
  url: file:./mastra.db

# or for Turso cloud:
storage:
  type: libsql
  url: libsql://my-db.turso.io
  auth_token: ${TURSO_TOKEN}
#8 Memory declarative Tier A ⏳ pending ▼

What it's for

Gives agents persistent, searchable memory across conversations. Supports sliding-window message history, semantic similarity recall (vector search), and a working-memory scratchpad for mid-conversation state. Maps directly to Mastra's Memory class.

Syntax

memory/chat-memory.yaml
vector: pg-vector
embedder: text-embedding-3-small
last_messages: 10
semantic_recall: true
working_memory: true
agent/support-agent.yaml
memory: chat-memory
# reads from memory/chat-memory.yaml
#9 Sub-agents declarative Tier A ⏳ pending ▼

What it's for

Lets an agent delegate tasks to other agents at runtime, enabling supervisor/multi-agent patterns. The parent agent can call child agents as if they were tools. Reuses the same resolver logic as the tools field.

Syntax

agent/supervisor-agent.yaml
name: Supervisor Agent
model: gpt-4o
agents:
  - research-agent
  - writer-agent
# emits: agents: { researchAgent, writerAgent }
#10 Guardrails / Processors declarative Tier A ⏳ pending ▼

What it's for

Attaches pre/post processing functions that intercept every prompt and response. Input processors run before the model (PII scrubbing, moderation, injection guards). Output processors run after (toxicity filters, response formatting). Essential for production deployments.

Syntax

agent/support-agent.yaml
input_processors:
  - pii-detector
  - moderation
output_processors:
  - toxicity-filter

Processor file

processor/pii-detector.ts
export default async function piiDetector(text: string) {
  return text.replace(/\b\d{3}-\d{2}-\d{4}\b/g, "[SSN]");
}
#11 Scorers / Evals declarative Tier A ⏳ pending ▼

What it's for

Attaches evaluation scorers that automatically grade agent responses on metrics like relevancy, toxicity, and faithfulness. Results feed into Mastra's eval dashboard, enabling quality monitoring and regression detection over time.

Syntax

agent/support-agent.yaml
scorers:
  - answer-relevancy
  - toxicity
  - faithfulness
#12 Run Limits declarative Tier A ⏳ pending ▼

What it's for

Prevents runaway agent loops by capping the number of tool-call steps and defining exit conditions. Maps to Mastra's defaultOptions.maxSteps and stop condition callbacks. Critical for cost control and predictable latency.

Syntax

agent/support-agent.yaml
max_steps: 10
stop_when: task_complete
# emits: defaultOptions: { maxSteps: 10 }
#13 Metadata declarative Tier A ⏳ pending ▼

What it's for

Attaches arbitrary key-value metadata to an agent for organizational and routing purposes. Useful for tagging agents by team, environment, or version — enables filtering in dashboards and multi-tenant setups.

Syntax

agent/support-agent.yaml
metadata:
  team: support
  version: "1.0"
  environment: production
#14 Observability / Tracing declarative Tier A ⏳ pending ▼

What it's for

Wires OpenTelemetry tracing into Mastra so every agent run, tool call, and LLM request emits spans to your observability backend (Honeycomb, Datadog, Langfuse, etc.). Essential for debugging latency and understanding model behavior in production.

Syntax

config.yaml
observability:
  provider: opentelemetry
  endpoint: https://otel.example.com
  service_name: my-assistant
#15 Workflows author-as-code Tier B ⏳ pending ▼

What it's for

Defines multi-step, branching pipelines of tool calls and agent invocations. Workflows give you deterministic control flow (sequences, branches, loops) on top of agents — ideal for complex tasks like research-then-write or ingest-then-summarize.

Syntax

workflow/research-workflow.ts
import { createWorkflow, createStep }
  from "@mastra/core/workflows";

export const researchWorkflow =
  createWorkflow({ id: "research-workflow" })
    .then(searchStep)
    .then(summarizeStep)
    .commit();
agent/research-agent.yaml
workflows:
  - research-workflow
#16 Structured Output author-as-code Tier B ⏳ pending ▼

What it's for

Forces the agent to respond with a validated JSON object matching a Zod schema instead of free text. Essential when the agent output is consumed programmatically — form fills, API payloads, database inserts.

Syntax

schema/support-response.ts
import { z } from "zod";

export const supportResponseSchema =
  z.object({
    resolved: z.boolean(),
    summary: z.string(),
    ticket_id: z.string().optional(),
  });
agent/support-agent.yaml
output: support-response
# reads from schema/support-response.ts
#17 MCP Tool Servers declarative Tier B ⏳ pending ▼

What it's for

Connects external Model Context Protocol (MCP) servers to the agent, giving it access to tools served over stdio or HTTP. This lets you plug in any MCP-compatible tool provider (filesystem, browser, databases, APIs) without writing TypeScript.

Syntax

mcp/filesystem.yaml (stdio)
command: npx
args:
  - "-y"
  - "@modelcontextprotocol/server-filesystem"
  - "/workspace"
mcp/remote-tools.yaml (HTTP)
url: https://tools.example.com/mcp
# emits: new MCPClient({ url: "..." })
#18 Custom Processors / Scorers author-as-code Tier B ⏳ pending ▼

What it's for

Write domain-specific processors and eval scorers in TypeScript that get imported verbatim by the codegen. Lets you go beyond Mastra's built-in catalog — custom business rule validators, proprietary toxicity models, or brand voice checkers.

Syntax

processor/brand-voice.ts
export default async function brandVoice(
  text: string
) {
  // enforce brand vocabulary
  return text.replace(/utilize/gi, "use");
}
scorer/relevancy.ts
import { createScorer }
  from "@mastra/evals";

export const relevancyScorer =
  createScorer({
    name: "relevancy",
    score: async ({ input, output }) =>
      computeRelevancy(input, output),
  });
#19 Voice declarative Tier B ⏳ pending ▼

What it's for

Attaches text-to-speech and speech-to-text capabilities to an agent using providers like ElevenLabs, OpenAI, or Deepgram. The codegen emits a new CompositeVoice(...) instantiation from the YAML config. Enables voice agents and telephony integrations.

Syntax

voice/default-voice.yaml
provider: elevenlabs
voice_id: rachel
stability: 0.5
similarity_boost: 0.75
agent/voice-agent.yaml
voice: default-voice
# emits: voice: new CompositeVoice(...)
#20 RAG author-as-code Tier C ⏳ pending ▼

What it's for

Retrieval-Augmented Generation — lets agents query a vector store to fetch relevant document chunks before generating a response. Involves two parts: an ingestion pipeline (chunking + embedding documents) and a vector-query tool the agent calls at runtime.

Syntax

tools/vector-query.ts
import { createVectorQueryTool }
  from "@mastra/rag";

export const vectorQueryTool =
  createVectorQueryTool({
    vectorStoreName: "pg-vector",
    indexName: "documents",
    model: "text-embedding-3-small",
  });
#21 Vector Stores declarative Tier C ⏳ pending ▼

What it's for

Registers named vector database connections that can be referenced by RAG tools and memory configs. Mastra supports PostgreSQL (pgvector), Pinecone, Qdrant, and others. Centralizing these in config.yaml avoids scattered connection strings.

Syntax

config.yaml
vectors:
  pg-vector:
    type: pg
    connection_string: postgresql://localhost/mydb
  pinecone:
    type: pinecone
    api_key: ${PINECONE_API_KEY}
    index: my-index
#22 Server / Auth Adapters hand-wired Tier C ⏳ pending ▼

What it's for

Exposes Mastra agents over HTTP using Express, Hono, or NestJS server adapters — adding REST endpoints, auth middleware, and CORS. Required when you need to serve agents as an API rather than running them as CLI scripts or serverless functions.

Syntax

server.ts
import { Mastra } from "@mastra/core";
import { createHonoServer } from "@mastra/server/hono";

const mastra = new Mastra({ /* generated config */ });
const app = createHonoServer(mastra);
app.listen(3000);
#23 Deployment hand-wired Tier C ⏳ pending ▼

What it's for

Packages and deploys the generated Mastra project to Cloudflare Workers, Vercel, or Netlify using Mastra's official deployer adapters. Each adapter handles bundling, environment variable injection, and platform-specific entry points.

Syntax

deploy.ts (Cloudflare Workers)
import { createCloudflareHandler }
  from "@mastra/deployer/cloudflare";
import { mastra } from "./mastra";

export default createCloudflareHandler(mastra);
#24 Workspaces / Sandboxes / Browser hand-wired Tier C ⏳ pending ▼

What it's for

Provides agents with access to isolated execution environments: filesystem workspaces (read/write files), code sandboxes (run arbitrary code safely), and a headless browser (scrape, screenshot, interact with web UIs). Enables autonomous computer-use agents.

Syntax

tools/sandbox.ts
import { createSandbox } from "@mastra/sandbox";

const sandbox = await createSandbox({
  runtime: "node",
});
await sandbox.execute("npm install lodash");
